## Rollback

1. If the migration fails, it rolls back the full transaction. Keep both ALB fixed-503 rules and the schedule disabled; record the SQLSTATE and confirm the additive schema transaction left no partial changes. Re-register the instance target, wait for V1 health, restore the original drain-delay setting, remove the two fixed-503 rules, then enable the schedule last.
2. If the migration succeeds but new-code deployment or smoke checks fail, keep both API rules active and the schedule disabled, roll Beanstalk back to the recorded V1 application version, register the instance target, and verify V1 health and a read/write smoke check. V1 ignores the additive nullable columns/indexes, so leave the schema in place and retain all new data. Restore the original drain-delay setting, remove both fixed-503 rules, then enable the schedule last.
3. Leave the additive schema in place for a fast-forward fix. A schema rollback is not the normal rollback: dropping the constraints, indexes, and columns loses new branch IDs and idempotency keys and can permit duplicate submissions. Restore from backup only for data corruption; never overwrite evaluations received after that backup.

The existing text `branch` and legacy `source` are never removed by this migration. Access method remains `UNKNOWN` because the existing URL is shared by QR, NFC, and links.

## Branch matching and expected lock behavior

Migration backfill uses exact equality `branches.client_id = evaluations.client_id AND branches.name = evaluations.branch`; it does not use `BTRIM`. A unique exact match inside that tenant is assigned. Zero matches, more than one match, or whitespace differences stay unassigned and appear in the report (the latter under `unmatched`). This intentionally differs from current intelligence issue aggregation, whose branch-scope comparison uses `BTRIM` on both stored branch values. The display/query normalization is not evidence that old evaluation text uniquely identifies a branch, so it does not authorize a fuzzy backfill.

The migration transaction holds table/schema locks through commit. Its `ALTER TABLE` operations can wait for an exclusive table lock; the row backfill and ordinary index builds also take time proportional to existing table sizes. The two configured limits bound lock wait and each statement, not total wall-clock time. A timeout aborts and rolls back the complete migration; investigate the blocker/runtime and rerun manually only after review. Measure on an isolated production-sized copy before scheduling; do not treat a small synthetic test runtime as a production estimate.

Isolated local verification (PostgreSQL 16.14): the first run processed 3 synthetic evaluations and 1 branch in 20.7 ms, reporting `matched=1`, `unmatched=2`, `ambiguous=0`, `no_branch=0`. After a V1-style legacy insert and rerun, the existing feedback/source values remained intact and the exact branch was assigned; the report was `matched=2`, `unmatched=2`, `ambiguous=0`, `no_branch=0`, with the rerun at 9.5 ms. These timings and row counts are test-fixture measurements only. A deliberately invalid check constraint produced SQLSTATE `23514`; the runner rolled the transaction back, left pre-transaction values untouched, and succeeded after manual repair. With a separate transaction holding a read lock on `evaluations`, migration returned SQLSTATE `55P03` after 5.05 seconds; the runner did not retry.

The operational write gate is the temporary fixed-503 rule on both ALB listeners; the operational drain is target deregistration after increasing its observed 20-second delay. The rule leaves the `/` target health check untouched. Pause the actual schedule first, retain both controls through migration/deployment/smoke checks, then restore the instance target and original target-group setting before removing the rules and enabling the schedule last. A one-instance target deregistration also interrupts all other app traffic until re-registration. If the migration fails, leave the schedule and API rules paused while restoring a healthy V1 target. These are future operator actions only; no production resource was changed during this review.
