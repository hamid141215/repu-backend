# Repu source phase 1: migration and rollback

This plan is for review. No production database or AWS resource was changed.

## Apply

1. Record the Beanstalk environment and database identifier in the change ticket. Take a verified database backup and record `evaluations`/`branches` row counts and the current application version.
2. Deploy the release bundle to the verified Node.js 22 AL2023 environment. Its `.platform/hooks/predeploy/50_repu_source_migration.sh` hook reads only `PG_URL` via the instance-local Elastic Beanstalk `get-config` utility and runs `db/run-repu-feedback-migration.js` before the new application starts. It verifies Node.js, the migration file, and the installed `pg` dependency; any missing prerequisite exits nonzero before connecting. The runner uses one transaction, a 5-second `lock_timeout`, a 10-minute per-statement `statement_timeout`, and a 30-second total deadline. At the total deadline it terminates the migration backend; PostgreSQL rolls back its open transaction as that backend exits. There is no grace period or automatic retry. If the migration cannot finish within 30 seconds, the hook fails and Beanstalk aborts the deployment; waiting clients are not automatically given a longer window. It emits only numeric branch-match counts and sanitized SQLSTATE/error codes, never `PG_URL` or customer data. Review nonzero `ambiguous` and `unmatched`; they stay unassigned.
3. The `.platform/hooks/postdeploy/90_repu_source_legacy_backfill.sh` hook performs only idempotent `UPDATE`s for legacy rows: it fills `source_kind` and assigns a branch only for a unique exact name match inside the tenant. It does not rerun `ALTER TABLE`, create indexes, or recreate constraints. This catches V1 rows written during the deployment gap without repeating structural migration. It uses the same hidden `PG_URL` and bounded transaction; failure returns nonzero and fails the deployment. After EB health is Green, verify the deployed version and both hook reports. Smoke-check a branch submission, same-key replay, changed-content conflict, client-wide submission, and masked phone in list APIs. Existing API traffic, health checks, and the hourly schedule continue through deployment. V1 `source` values and downstream jobs remain active.

## Rollback

1. If the predeploy migration fails or reaches its 30-second deadline, the hook exits nonzero and Beanstalk aborts deployment. PostgreSQL rolls back the terminated backend's open transaction. Confirm no partial DDL/data changes and retain the running V1 application; record only the SQLSTATE/operation code. Do not add an automatic retry or extend the deadline.
2. If migration succeeds but deployment, postdeploy backfill, or smoke checks fail, roll Beanstalk back to `repu-v1-5f9456d-committed-linux1` (or the recorded V1 application version) and verify V1 health plus a read/write smoke check. V1 ignores additive columns/indexes, so leave the schema in place and retain all new data. If only postdeploy backfill failed, rerun its data-only mode after the fix; do not rerun DDL to reconcile legacy rows. Normal API traffic and the hourly schedule remain enabled throughout rollback.
3. Leave the additive schema in place for a fast-forward fix. A schema rollback is not the normal rollback: dropping the constraints, indexes, and columns loses new branch IDs and idempotency keys and can permit duplicate submissions. Restore from backup only for data corruption; never overwrite evaluations received after that backup.

The existing text `branch` and legacy `source` are never removed by this migration. Access method remains `UNKNOWN` because the existing URL is shared by QR, NFC, and links.

## Branch matching and expected lock behavior

Migration backfill uses exact equality `branches.client_id = evaluations.client_id AND branches.name = evaluations.branch`; it does not use `BTRIM`. A unique exact match inside that tenant is assigned. Zero matches, more than one match, or whitespace differences stay unassigned and appear in the report (the latter under `unmatched`). This intentionally differs from current intelligence issue aggregation, whose branch-scope comparison uses `BTRIM` on both stored branch values. The display/query normalization is not evidence that old evaluation text uniquely identifies a branch, so it does not authorize a fuzzy backfill.

The migration transaction holds table/schema locks through commit. Its `ALTER TABLE` operations can wait for an exclusive table lock; the row backfill and ordinary index builds also take time proportional to existing table sizes. The 5-second lock timeout, 10-minute per-statement timeout, and 30-second total deadline apply together; the total deadline bounds the deployment migration wait. At 30 seconds the runner terminates its own PostgreSQL backend, which causes PostgreSQL to roll back the transaction and release locks. Investigate any timeout and retry only in a separately reviewed deployment; the hook itself does not retry or extend the wait. Measure on an isolated production-sized copy before scheduling; do not treat a small synthetic test runtime as a production estimate.

Isolated local verification (PostgreSQL 16.14): the first run processed 3 synthetic evaluations and 1 branch in 20.7 ms, reporting `matched=1`, `unmatched=2`, `ambiguous=0`, `no_branch=0`. After a V1-style legacy insert and rerun, the existing feedback/source values remained intact and the exact branch was assigned; the report was `matched=2`, `unmatched=2`, `ambiguous=0`, `no_branch=0`, with the rerun at 9.5 ms. These timings and row counts are test-fixture measurements only. A deliberately invalid check constraint produced SQLSTATE `23514`; the runner rolled the transaction back, left pre-transaction values untouched, and succeeded after manual repair. With a separate transaction holding a read lock on `evaluations`, migration returned SQLSTATE `55P03` after 5.05 seconds; the runner did not retry.

This deployment path does not require an ALB API gate, target deregistration, target-group delay changes, or pausing `repu-intelligence-hourly`. Those earlier cutover steps are superseded: the bounded transaction either commits within 30 seconds or is terminated and rolled back, and Beanstalk fails the deployment on hook failure. API requests and scheduled analysis continue normally; operations that contend for migration locks may wait up to configured database/client limits. Do not extend the deployment deadline to accommodate them. No production resource was changed during this review.
